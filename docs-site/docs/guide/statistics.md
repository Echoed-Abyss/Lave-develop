# 消息统计

统计 Tab 是应用的首页（五个 Tab 的正中间）。它只回答两个问题：
**收到多少、发出多少**。

## 口径

| 指标 | 计数时机 | 为什么是这个时机 |
| --- | --- | --- |
| 收到消息 | **去重之后** +1 | 官方明确「相同 `msg_id` 可能重复推送」。在去重前计数，一次消息会被算成两次，数字持续虚高 |
| 发出消息 | **发送成功之后** +1 | 把失败也计进去，用户会以为「发了很多」，与实际体验相反 |

只统计**消息**本身，不含入群、推送开关这类生命周期事件。
把它们混进来会让「收消息数」虚高，而用户看这个数字是想知道
「这个机器人一天到底处理了多少条消息」。

## 数据怎么存

维护的是**按天聚合的计数器**，而不是从历史记录里现算。

原因很具体：历史仓库按会话分片、每个会话只保留 500 条，
从那里算「总收发量」既不准（老数据已被截断）也慢（每渲染一帧都要遍历全部消息）。

按天计数还有一个额外好处：折线图需要「某天没有消息」这个信息，
而从历史里现算是拿不到它的——那天的数据可能只是被截断了。

| 项目 | 说明 |
| --- | --- |
| 落盘 | 与其它数据同一个 JSON 文档，键名 `stats` |
| 防抖 | 3 秒。消息密集时每条都写盘会造成 IO 抖动 |
| 退出时 | 应用退出前会补一次立即写入，避免丢掉最后几条计数 |
| 保留 | 最多 730 天（两年）。一条记录只有几十字节，裁剪反而要额外维护一份累计总数 |

累计数**不随裁剪倒退**：裁剪只删除最老的日期，累计是「历史总量」。

## 折线图

- 三种时间范围：7 / 14 / 30 天；
- **缺失的日期必须补零**。只画有数据的天会让横轴被压缩，
  「某天完全没有消息」这个事实就看不见了——而它恰恰是最该被注意到的；
- 点选任意一天可以看到当天的确切数字，再点一次取消选中；
- 折线图是手写的 `CustomPainter`，没有引入图表库：
  只需要两条折线，图表库带来的体积与 API 面积远大于收益，
  而且主题配色（网格线用边框色、文字用次要色）反而要写更多代码去覆盖。

## 已知边界

- 统计**从本功能上线时开始累积**，不包含此前的历史消息；
- 目前只有收发总量，没有按机器人 / 按会话拆分，也没有失败率与延迟维度；
- 统计不区分「被动回复」与「主动消息」，两者都算「发出」。
