# 故障排查

按「症状」查，每条都给出**先看哪里**，而不是一串可能性。

## 机器人连上了但收不到任何消息

::: danger 首要怀疑 intents

官方原文：如果在鉴权的时候传递了无权限的 `intents`，`websocket` 会报错，
并直接关闭连接。除了 `GUILDS`、`PUBLIC_GUILD_MESSAGES`、`GUILD_MEMBERS`
是基础事件默认有权限之外，其他的特殊事件都需要经过申请才能够使用。

:::

也就是说**多订阅一位就可能让连接建不起来**，表现为「一直重连、日志里没有任何事件」。

怎么办：

1. 到「设置 → 事件订阅范围」把所有可选位**全部关掉**（只留必需位），再重连；
2. 到开放平台确认「单聊消息」「群聊消息」权限已开通；
3. 若日志里有 `4013` / `4014`，说明就是想订阅无权限的位——
   应用会自动降级并回写设置，此时只需确认降级后的掩码是否符合预期。

还有一条最容易误判的官方说明：**权限被取消后，当前连接不报错但收不到
对应事件，重连才会报错**。所以「昨天正常、今天收不到」同样先查权限。

## 应用退到后台后连接很快就断

日志特征：反复出现「连接被关闭：1002」，连接只活几十秒到两分钟。

原因是进程被系统冻结（`cached apps freezer`），不是协议实现问题。
处理办法与无法对抗的场景见 [后台保活](keep-alive.md)。

排查时看连接关闭日志里的**「距离最后一次收到数据过了多久」**：

- 超过一个心跳周期 → 进程当时已收不到东西，属于冻结或断网；
- 小于一个心跳周期 → 收发链路是通的，问题更可能在协议层。

## 机器人不回复指令 / 回复失败

先看日志里有没有这两句：

| 日志 | 含义 | 处理 |
| --- | --- | --- |
| `msg_id 与 event_id 只能二选一` | 请求同时带了两个互斥字段 | 属于历史缺陷，当前版本已用 `PassiveCredential` 类型从根上排除 |
| `被动回复已过有效期` | 群聊 5 分钟 / 单聊 60 分钟窗口已过 | 应用会自动改发主动消息并记 WARN |
| `本消息的被动回复次数已用尽` | 群聊 5 次 / 单聊 4 次 | 同上 |
| `被动回复窗口已关闭，跳过回复`（插件日志） | 插件自己判定了 `can_reply = false` | 说明事件里的 `can_reply` 为 false，属正常保护 |

另外注意：**主动消息可能被用户关闭**。会话页顶部或会话摘要上会显示
「主动消息已关闭」，此时任何主动消息都会失败。

## 头像显示的是灰色默认头像

头像走腾讯的头像 CDN（`AppID + openid`）。**该 CDN 对无效 openid 不返回 404，
而是返回 200 + 一张默认灰头像**，因此：

- 看到灰头像**不等于代码出错**；
- 对方本来就没设置头像时，也是同一张灰图；
- 群聊会话拿不到群头像（CDN 对群 openid 只返回默认灰头像），
  界面统一用群图标占位。

单聊对方的头像应该能在几秒内出现；不出现则检查网络能否访问 `q.qlogo.cn`。

## 插件不工作

按顺序确认这四件事：

1. **平台支不支持**：插件页顶部的能力横幅会直接说明原因。
   iOS 完全不支持（无法创建子进程）；Android 缺内置运行时也会不可用。
2. **开关是否打开**：关闭状态的插件不会启动。已启用的插件在应用启动时会**自动拉起**。
3. **状态是不是「运行中」**：只有收到插件的 `ready` 才算运行中。
   如果停在「启动中」然后变成「已崩溃」，看 `lastError`——常见是导入阶段抛异常
   或握手超时。
4. **事件是否订阅**：`plugin.json` 的 `events` 为空表示订阅全部；
   写了具体列表就只有那些事件会投递给它。

更多见 [插件生命周期与故障](../plugins/lifecycle.md)。

## 插件反复重启 / 显示「无响应」

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 已崩溃 | 进程异常退出 | 看卡片上的错误详情；应用会在预算内自动重启 2 次，之后停下 |
| 无响应 | 连续 3 次心跳未回复（约 90 秒静默） | 通常意味着死锁或长时间阻塞调用。应用会结束该进程并计入崩溃 |

「无响应」与「已崩溃」是两种不同故障，界面刻意分开显示：
卡死的进程还活着、还占着内存，只是不再处理任何消息。

## 插件日志丢了很多行

日志有**每秒行数上限**（默认 40 行/秒），超限会被丢弃并计数。
插件详情里的「丢弃日志」会显示丢了多少。

看到这个数字通常说明插件里有死循环 `print`——先去看插件代码，
而不是调高上限。

## 统计数字不动

- 统计**从本功能上线时开始累积**，不包含此前的历史消息；
- 「发出」只在**发送成功**后 +1，失败不计；
- 若一直为 0，先确认消息确实收到了（看「日志」页有没有「群聊消息：…」）。

## 应用启动后白屏几秒

首次安装后第一次启动插件时需要释放 Python 标准库（653 个文件）。
本项目把这个动作**推迟到「首次启动插件」**，因此：
启动应用本身不会白屏，启动第一个插件时会稍慢一次。

如果每次启动插件都慢，说明标准库释放标记没生效，检查应用私有目录是否可写、
以及磁盘是否还有空间。

## 构建失败

见 [从源码构建](../getting-started/build.md) 的「本机构建踩过的坑」一节：
C 盘空间不足、Kotlin 增量缓存损坏、Gradle 发行包下载被截断——
这三条的报错都很有误导性。

## 该收集哪些信息去求助

「日志」页右上角的**复制诊断信息**会把日志导出为文本（密钥已脱敏）。
官方接口失败时日志里会带 `官方错误码` 与 `trace_id`——
后者是找平台协助时唯一有效的凭据。
