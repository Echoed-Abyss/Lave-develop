# 架构概览

## 一句话

手机就是机器人客户端：**直连官方 Gateway WSS 收事件，直连官方 HTTP API 发消息**，
中间没有任何自建服务。

```
        ┌──────────────────── 手机（本应用） ────────────────────┐
        │                                                        │
        │  UI 层（5 个 Tab）                                     │
        │   统计 / 机器人 / 日志 / 插件 / 设置                    │
        │        │ 订阅 ChangeNotifier                          │
        │  ┌─────▼──────────────────────────────────────────┐    │
        │  │ 应用装配 AppServices（手写容器 + 明确的启动顺序）│    │
        │  └─────┬──────────────────────────────────────────┘    │
        │        │                                               │
        │  ┌─────▼────────┐   ┌──────────────┐   ┌───────────┐   │

        │  │ Registry     │──▶│ 去重/归一/落库 │─▶│ 子进程+JSON│ │
        │  │ 每个机器人一条│   └──────┬───────┘   └───────────┘   │
        │  └─────┬────────┘          │                           │

```

## 分层与目录

```
lib/
  app/          应用装配（服务容器）、主题、Tab 注册、保活协调器
  core/         环境配置、官方常量与端点、协议枚举、错误体系、日志、工具
  data/         本地存储（JSON 文档）与仓库（账号/消息/统计）
  domain/       领域模型与指令引擎（纯 Dart，无 Flutter 依赖）
  gateway/      WSS：接入点、连接状态机、心跳、协议解析、事件分发
  plugins/      Python 插件子进程运行时与管理器
  features/     UI：统计 / 机器人 / 会话 / 日志 / 插件 / 设置
  shared/       玻璃组件集（GlassPanel / GlassExpandableCard / GlassLogItem …）
```

分层的意义不在于「好看」，而在于**改动的半径可控**：官方改了字段名，
改动被限制在 `gateway/protocol/` 下的解析层；UI 想换一套皮肤，
只动 `shared/` 与 `app/theme.dart`。

## 关键设计决策

### 1. 为什么是「手写容器」而不是让 Riverpod 逐层构建

这些服务之间有**明确的启动顺序**：先恢复本地数据（否则任何一步失败都没有日志可查）
→ 探测插件平台能力（结论要写进日志）→ 起保活前台服务（必须早于建连接）
→ 最后才建连接（连接会持续产生事件）。

手写装配让这个顺序在 `AppServices.initialize()` 里一目了然，
也避免了异步 Provider 之间的隐式依赖。Riverpod 仍然负责把容器注入 UI 树。

### 2. 为什么每个机器人一条独立连接

官方的 `session_start_limit` 是**按 Bot 维度**计算的，多个机器人同时在线不会互相挤占配额。
因此 `ConnectionRegistry` 按 `botId` 维度组织：独立连接、独立分发器、独立代发通道。

代价是耗电与内存随连接数线性上升，所以并发数上限 3（`AppConfig.maxConcurrentConnections`），
超出时界面会拒绝启用并说明原因，而不是静默失败。

### 3. 为什么事件要「归一化」后才交给 UI 与插件

官方原始 JSON 里同一件事有四种 openid（`id` / `union_openid` / `user_openid` /
`member_openid`），还有 RFC3339 字符串与 Unix 秒混用的时间字段。
领域层把它们收敛成 `ActorRef`（「在这个会话里，是谁」）与 `DateTime`。

好处是**官方改字段名不会直接打断插件**——插件看到的是稳定结构。

### 4. 为什么插件是独立进程

见 [插件系统总览](../plugins/index.md)。一句话：让「插件崩溃」只影响插件。

## 数据都存在哪

| 数据 | 位置 | 说明 |
| --- | --- | --- |
| 账号配置、日志、事件、统计、插件开关 | 单个 JSON 文档 | 应用文档目录下的 `lave_store.json` |
| AppSecret / Bot Token | 系统安全存储 | Android Keystore 加密；不进 JSON 文档 |
| Python 运行时标准库 | 应用私有目录 | 首次启动插件时释放 |
| 插件代码与插件数据 | 应用文档目录下的 `plugins/<id>/` | `data/` 子目录是插件的可写数据区 |

选择单 JSON 文档而不是数据库：drift / sqflite 需要代码生成或额外原生依赖，
多一层构建步骤就多一类「生成物过期导致编译失败」的问题。
自用场景的数据量（消息、日志各按千条上限）完全够用，
升级路径集中在几个 `xxxStoreLike` 接口后面。

::: info 写入是并发安全的

`JsonDocStore` 维护「内存即真相 + 串行写入链」。
早期版本是「读文件 → 改 → 整份写回」，四个写入方（账号、日志、设置、插件状态）
并发时会让彼此的数据静默消失。

:::
