# 网关连接

这一页解释「为什么连不上 / 为什么连上了却没消息」，是排查问题的第一站。

## 建连流程

```
① POST /app/getAppAccessToken      ← appId + clientSecret 换 access_token（2 小时）
② GET  /gateway/bot                ← 拿 WSS 地址（顺便拿到 session 剩余额度）
③ WSS  连接 → 等 Op10 Hello        ← Hello 里给出心跳周期（实测 41250 毫秒）
④ 发 Op2 Identify（带 intents）
   或 发 Op6 Resume（带 session_id + seq）
⑤ 收到 READY / RESUMED 即为在线
```

第 ① 步有个必须知道的坑：**这个接口失败时 HTTP 仍返回 200**，
必须读响应体的 `code`，不能用状态码判断成败。

第 ② 步的返回值**必须使用**，不要硬编码域名——官方文档里的
`wss://api.bot.qq.com/websocket/` 只是示例。该接口限频 2 QPM，
因此本项目对结果做了缓存（缓存不是优化，是避免触发限流的必要措施）。

## intents：最容易把机器人变成哑巴的地方

::: danger 官方原文

事件类型的订阅，是有权限控制的，除了 `GUILDS`，`PUBLIC_GUILD_MESSAGES`，
`GUILD_MEMBERS` 事件是基础的事件，默认有权限订阅之外，其他的特殊事件，
都需要经过申请才能够使用，**如果在鉴权的时候传递了无权限的 `intents`，
`websocket` 会报错，并直接关闭连接**。
请开发者注意订阅事件的范围需要控制在自己所需要的范围之内。

:::

注意后果是**关闭连接**，不是「收不到那一类事件」。因此「多订阅一位」这件事的代价
不是少收点消息，而是完全连不上——现象是反复重连、日志里没有任何事件。

本项目的处理方式：

| 行为 | 理由 |
| --- | --- |
| 默认只订阅**必需的一位** `GROUP_AND_C2C_EVENT (1<<25)` | 它覆盖单聊消息、群 @消息、机器人进出群、好友增删，是「机器人能用」的最小集合 |
| 其余可选位在「设置」页逐个开启 | 让用户在确认自己申请到权限之后再打开 |
| `GROUP_MEMBER_EVENT (1<<24)` 标红提示 | 这一位**不在官方 intents 总表里**（只出现在几个事件页的 Intent 字段中），风险最高 |
| 被 4013 / 4014 拒绝时**自动降级**到必需位并重试 | 直接停止重连等于「永远收不到消息」，而去掉无权限的位就能恢复 |

还有一条容易误判的官方说明：**权限被取消后，当前连接不报错但收不到对应事件，
重连才会报错**。所以「昨天正常、今天收不到」也应先查权限。

完整的 intent 位表见 [事件订阅 intents](../reference/intents.md)。

## 心跳

| 细节 | 说明 |
| --- | --- |
| 周期 | **由服务端的 Hello 下发**（实测 `41250` 毫秒），不是客户端写死的 |
| 载荷 | `op = 1`，`d` 为**客户端收到的最新 `s`**，首次连接传 `null` |
| 确认 | 服务端回 `Op11 Heartbeat ACK` |
| 发送频率 | 必须按 Hello 给的周期发；本项目用 `Timer.periodic` 严格按周期发送 |

::: info 官方未提供心跳丢失的判定阈值

这是官方文档的缺口（`知识库` 第 11 章列为缺失项）。本项目取
「连续丢失次数 ≥ `heartbeatTimeoutMultiplier`（默认 2）」即判定死链并重连。
阈值可在 `AppConfig` 里调。

:::

心跳停发会怎样？服务端会关闭连接。而**什么会让心跳停发**是另一个问题——
应用退到后台被系统冻结时，Dart 的定时器不再触发，心跳就断了。
这是「后台掉线」的根因，详见 [后台保活](keep-alive.md)。

## 重连策略

断线后按**指数退避 + 抖动**重连：2s / 4s / 9s / 18s / 37s…直到上限。
加抖动的目的是避免多个机器人在同一时刻一起重连。

重连时优先 `Resume`（带 `session_id` + `seq`，服务端会补发遗漏事件）；
只有在服务端明确要求重新鉴权时才改走 `Identify`。

## 关闭码处置

官方错误码表的两列（「是否可以重试 RESUME」「是否可以重试 IDENTIFY」）
就是本项目的处置依据：

| 关闭码 | 含义 | 可 RESUME | 可 IDENTIFY | 本项目的处置 |
| --- | --- | --- | --- | --- |
| 4001 | 无效的 opcode | 否 | 否 | 停止重连并标记为阻塞态 |
| 4002 | 无效的 payload | 否 | 否 | 停止重连并标记为阻塞态 |
| 4006 | 无效的 session id，无法继续 resume，请 identify | 否 | **是** | 改走 Identify |
| 4007 | seq 错误 | 否 | **是** | 改走 Identify |
| 4008 | 发送 payload 过快 | **是** | **是** | 退避后 Resume |
| 4009 | 连接过期，请重连并执行 resume | **是** | **是** | 退避后 Resume |
| 4010 | 无效的 shard | 否 | 否 | 停止重连（本项目不分片） |
| 4011 | 连接需要处理的 guild 过多 | 否 | 否 | 停止重连 |
| 4012 | 无效的 version | 否 | 否 | 停止重连 |
| 4013 | 无效的 intent | 否 | 否 | **自动降级 intents 后重试一次** |
| 4014 | intent 无权限 | 否 | 否 | **自动降级 intents 后重试一次** |
| 4900~4913 | 内部错误，请重连 | 否 | **是** | 退避后重连 |
| 4914 | 机器人已下架，只允许连接沙箱环境 | 否 | 否 | 停止重连并提示 |
| 4915 | 机器人已封禁，不允许连接 | 否 | 否 | 停止重连并提示申请解封 |

::: tip 4013 / 4014 为什么要处理成「能恢复」

官方对这两者标注「两个都不可重试」，但那是指**用同样的 intents 重试无意义**。
如果因此直接进入终态停止重连，用户看到的是「连不上且永远收不到消息」，
而实际上只需要去掉无权限的那几位就能恢复。因此本项目先降级再试一次，
只有连必需位都被拒才判定为终态。

:::

## 分片

官方 `GET /gateway/bot` 返回 `shards` 建议值（通常为 1）。
本项目**不分片**：个人自用场景的机器人规模远达不到需要分片的量级，
引入分片只会带来 `shard` 参数错误（4010）这类额外故障面。
因此日志里会记录「官方建议分片 N，本项目不分片」，便于对照。

## 诊断入口

连接被关闭时，日志里会附带**距离最后一次收到数据过了多久**：

- 该时长 < 一个心跳周期 → 收发链路当时是通的，问题更可能在协议层；
- 该时长 ≥ 一个心跳周期 → 进程当时已经收不到东西（被冻结或断网），
  而不是协议层被拒绝。

这一条把「协议实现错了」与「进程被系统冻结了」区分开，
省去了在这两类完全不同的原因之间来回猜的时间。
