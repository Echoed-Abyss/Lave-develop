# 内置命令与插件的边界

插件作者最常踩的坑不在协议本身，而在「消息到底会不会轮到我」。这一页讲清楚
主程序自己会消费哪些消息、哪些会原样交给插件，以及两者重叠时谁优先。

## 内置的三条命令

主程序自带三条命令，全部以 `#` 开头，不依赖任何插件：

| 命令 | 行为 |
| --- | --- |
| `#help` | 列出当前全部可用指令（含插件通过 `CommandEngine.register` 注册的） |
| `#ping` | 回一句 `pong`，附带会话场景与本条消息剩余的被动回复次数 |
| `#status` | 输出会话 id、被动回复窗口剩余时间、本消息剩余可回复次数 |

它们刻意只有三条。指令越多越难维护，真正的业务逻辑应该写成插件——
插件有独立的崩溃隔离与启停控制，改坏了不会连累机器人本身。

## 优先级：注册过的命令优先，其余一律放行

判断顺序是这样的：

```
消息到达
  ├─ 内容以 # 开头，且名字在已注册表里   →  内置/已注册命令消费，插件收不到
  ├─ 内容以 # 开头，但名字没注册过       →  放行，交给插件
  └─ 内容不以 # 开头                     →  直接交给插件
```

第二条是重点。**`#` 不是内置命令的保留前缀**：插件完全可以把自己的触发前缀
设成 `#hi`、`#签到` 之类，只要名字不和那三条撞上，消息就会正常投递到插件。

这一条曾经是错的——早期版本对所有 `#` 开头的消息一律返回「已消费」，
于是用了 `#` 前缀的插件永远收不到消息。表现很有迷惑性：插件页显示「运行中」、
日志里也写着「已就绪」，但发什么都没反应。示例插件当时用的正是 `#hi`，
所以这个 bug 一直藏在「示例插件也这样」的表象里。

## 撞名了会怎样

如果插件的触发前缀恰好是 `#help` / `#ping` / `#status`，插件**收不到**这条消息。
这不是可以绕过的实现细节，而是优先级本身：内置命令已经回复了，
再来一份插件的回复只会让同一个问题答两遍。

所以给插件选触发前缀时，避开这三条即可。用一个不同的前缀（如 `/hi`）
比用 `#` 加一个容易撞车的词更稳妥。

## 插件怎么知道消息没人管

主程序在下面这个条件下才会提示「收到未知指令：…（可用 `#help` 查看全部指令）」：

- 内置命令表里没有这个名字，**并且**
- 当前没有任何插件订阅这条事件（`events` 为空视为订阅全部）

有插件在场时不会插这句话。否则用户在插件已经正常回复的情况下，
还会看到一句「未知指令」，反过来怀疑插件没生效。

## 插件注册自己的命令

Dart 侧可以用 `CommandEngine.register` 把命令注册进内置表，
注册后它们同样优先于插件事件投递。这条路径是留给应用内扩展的，
Python 插件**用不到**——插件只能通过 `event` 收消息、通过 `reply` 发消息，
没有注册指令的通道。想在插件里实现「指令」，就是自己比对消息前缀。

```python
TRIGGER = host.config.get("trigger") or "/hi"

def on_event(host, envelope, payload):
    event = payload.get("event") or {}
    content = (event.get("content") or "").strip()
    if not content.startswith(TRIGGER):
        return                      # 前缀不匹配就安静返回，不要刷日志
    # 前缀匹配上了，再走回复流程（注意先看 event.can_reply）
```

## 前缀匹配要注意的两件事

`content.startswith(TRIGGER)` 是最省事的判定，但有两个边界值得留意。

第一，群聊 @ 消息的 `content` 已经由官方去掉了 @ 前缀，不需要自己剥。
这一点在[通信协议](protocol.md)的事件字段表里也写了。

第二，`startswith` 会把 `#hi` 和 `#history` 一起匹配上。
如果前缀可能被别的词包含，加一个分隔判定更稳：

```python
rest = content[len(TRIGGER):]
if rest and not rest[0].isspace():
    return                          # 是 #history 而不是 #hi
```
