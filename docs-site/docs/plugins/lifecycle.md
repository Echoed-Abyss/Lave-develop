# 生命周期与故障

插件的状态机、故障判定，以及主程序会自动做什么。

## 状态

| 状态 | 含义 | 有进程 | 可启动 |
| --- | --- | --- | --- |
| 已禁用 | 用户手动关闭了开关 | ❌ | ✅ |
| 未启动 | 已启用但尚未拉起 | ❌ | ✅ |
| 启动中 | 进程已创建，等待 `ready` | ✅ | ❌ |
| 运行中 | 握手完成，可收发事件 | ✅ | ❌ |
| 停止中 | 已发出 `shutdown`，等待退出 | ✅ | ❌ |
| **无响应** | 进程还在，但连续 3 次心跳无回复 | ✅ | ✅ |
| 已崩溃 | 进程异常退出 | ❌ | ✅ |
| 平台不支持 | 当前平台无法运行 Python 子进程 | ❌ | ❌ |

!!! note "「无响应」为什么单独列一个状态"

    卡死的进程**仍然占着内存**，而且事件会继续往它的 stdin 里堆。
    这类故障早期完全不可见——界面显示「运行中」，用户只在疑惑
    「插件怎么没反应」。把它单独提出来后，界面能说清故障性质，
    并给出「停止」按钮。

## 启动流程中的拦截

启动不是「拉起进程就完事」，中间有三道校验，顺序是刻意的：

```
① 协议版本检查  ──▶ 不兼容 → 拒绝加载（记为崩溃，附原因）
② 必填配置检查  ──▶ 缺失   → 拒绝启动（记为崩溃，附「缺哪几项」）
③ 创建进程      ──▶ 失败   → 记为崩溃
④ 下发 init + 等 ready（20 秒）──▶ 超时 → 结束进程并记为崩溃
⑤ 开始投递事件 + 心跳
```

!!! note "「拒绝启动」也会计入崩溃次数"

    上面 ①② 两道校验失败时，状态会落到**已崩溃**、崩溃次数 +1。

    这不是笔误，而是刻意的：对用户而言，这三类失败（协议不兼容、配置没填、
    进程起不来）的处置动作完全一样——都是**去看 `lastError` 说了什么**。
    如果给配置缺失单独发明一个状态，用户就要多学一个概念，而「崩溃」这个词
    恰好准确地表达了「它现在没在工作，而且有原因可查」。

    区别只在 `lastError` 的文案，以及校验 ①② 不会触发自动重启
    （反复拉一个注定起不来的进程没有意义）。

### 为什么握手要等 `ready`

早期实现把「进程创建成功」当作「运行中」，于是插件在导入阶段抛异常或卡住时，
界面依然显示「运行中」，用户完全看不出插件其实没有工作。

现在只有收到 `ready` 才算运行中。**在此之前的事件不会被投递**——
避免插件在自身初始化尚未完成时被唤醒。

## 心跳与卡死判定

| 参数 | 默认值 |
| --- | --- |
| 心跳间隔 | 30 秒 |
| 判定阈值 | 连续 3 次无响应（约 90 秒完全静默） |

第一帧心跳在握手完成时立刻发出，之后每 30 秒一次。
每个周期只统计**上一个周期有没有被回应**，所以「连续 3 次」正好对应
90 秒的完全静默，而不是 120 秒。

超时后主程序会：

1. 记一条 error（含可能的原因）；
2. 把状态标为**无响应**；
3. **结束该进程**——它仍占着内存，事件还会继续堆进它的 stdin；
4. 走下面的自动重启流程。

阈值取 3 次而不是 1 次，是为了避免误杀：插件正常处理一条消息也可能占住
事件循环几百毫秒。而 90 秒的完全静默基本只可能是死锁或长时间阻塞调用。

## 崩溃与自动重启

非预期退出时：

1. 记录崩溃原因（退出码，或由「为什么主动结束它」覆盖成更可读的文案）；
2. 崩溃次数 +1（**持久化**，跨重启累计）；
3. 若插件仍处于启用状态，按**预算**自动重启。

| 参数 | 默认值 |
| --- | --- |
| 最大自动重启次数 | 2 次（按会话计） |
| 退避 | 第 1 次等 2 秒，第 2 次等 4 秒 |

预算用尽后停止自动重启，并记一条 warn 提示去看崩溃原因。
预算会在两种情况下被重置：**稳定运行超过 5 分钟**，或**用户在界面上点了「重启」**。
前者是因为一个插件不该因为一天里偶发崩了两次就再也无法自动恢复；
后者是因为用户亲自动手往往意味着他刚改完代码或配置想再试一次，
此时还卡在旧额度上会让人以为按钮坏了。

### 为什么从「一律不重启」改成「有预算的重启」

早先的设计是「崩溃后一律不自动重启」，理由是怕崩溃循环耗电。
但那个策略把**瞬时故障**也一并放弃了：被系统内存压力杀掉、上游网络抖动导致
插件自己退出——这些情况下插件本可以自愈，用户看到的却是
「插件莫名其妙不工作了」。

有预算的退避重启兼顾两头：真正有缺陷的插件两次之后就会停下并保持「已崩溃」，
不会形成循环；偶发故障能在几秒内恢复。

## 主动停止不算崩溃

用户点「停止」、关闭开关、删除插件、退出应用，这些都属于**主动停止**：

- **不计入崩溃次数**；
- **不触发自动重启**。

!!! danger "这曾经是个缺陷"

    早期实现无法区分「插件崩了」与「我让它停的」，
    于是**用户每点一次「停止」，插件就多记一次「已崩溃」**。
    崩溃计数与「反复崩溃」提示因此全部失真。

    现在停止流程会先登记「这是主动停止」，再动进程——顺序不能反，
    因为退出事件是异步派发的。

另外，早先版本还有一个直接的 bug：`stop()` 把「正在停止」标志置位之后
才调用 `send()`，而 `send()` 会检查该标志并直接返回，于是
**`shutdown` 消息从来没被真正发出去**，每次停止都只能等满 3 秒宽限期再 SIGKILL。
现在停止流程直接写 stdin，不再依赖那个标志位的时序。

## 日志限流

| 参数 | 默认值 |
| --- | --- |
| 每插件日志上限 | 40 行/秒 |

超限的行会被丢弃并累计计数。计数不会每丢一行就刷新一次界面——那样限流本身
就成了新的性能问题——而是**每累计 100 行**才更新一次「丢弃日志」的数字，
并同时记一条 warn。所以界面上看到的是 1、101、201 这样的台阶，
不是连续增长。

限流的必要性很具体：插件在死循环里 `print`，每行都会触发
「日志服务通知界面 + 排队写盘」，几千行足以让界面卡住几秒。

**丢弃必须可见**：不显示丢了多少的话，排障时会以为插件没有输出。

## 什么时候会自动启动

有三个时机，都是「用户已经表达过要它跑」的情况：

| 时机 | 行为 |
| --- | --- |
| 应用启动 | 依次拉起全部「已启用但没在跑」的插件，每个之间间隔 400 毫秒 |
| 拨开启用开关 | 立刻启动该插件（启用即启动） |
| 覆盖导入插件包 | 导入前本来在跑的插件，导入完成后继续跑 |

!!! danger "这里曾经有两个坑"

    其一，早期版本的 `refresh()` 只把状态置为「未启动」，**没有任何地方去启动它们**。
    于是每次冷启动之后，用户明明开着插件，它却一直是「未启动」——
    界面看起来没坏，但机器人对消息毫无反应，只能手动去点启动。

    其二，拨开启用开关时也只置状态、不启动进程，用户必须再点一次「启动」。
    这个两步操作同样会被读成「装了没用」。

逐个错开而不是并发启动：同一瞬间拉起多个解释器会让冷启动明显变卡，
而且内置 Python 首次还要释放标准库（653 个文件）。

## 重新扫描时保留实时状态

插件目录的扫描结果来自磁盘，而进程状态只存在于内存。
重新扫描时两者会合并，否则「运行中」会被抹成「未启动」——
而进程其实还活着。界面与实际状态不一致是最难排查的一类问题。

## 用户能做什么

| 想要的效果 | 操作 |
| --- | --- |
| 启用并跑起来 | 拨开卡片的开关（启用即启动） |
| 临时停一下 | 点「停止」（停进程，保留启用状态与配置） |
| 崩溃/无响应后重来 | 点「重启」（会重置本次会话的自动重启预算） |
| 看崩溃原因 | 卡片上的红色错误块，以及「日志」页筛 `插件` 来源 |
| 彻底清干净 | 「删除」会停进程并删掉目录、配置、状态 |
