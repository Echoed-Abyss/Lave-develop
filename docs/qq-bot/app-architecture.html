这套架构的关键性质
  • 事件链路零后端：WSS 由设备主动外连腾讯网关，不需要公网 IP、不需要服务器、不需要域名与证书。这是官方对 WebSocket 通道的定位（「不依赖公网服务器部署，适合个人单机使用」）。
  • 数据主权在设备：消息历史、事件日志、session/seq 全部落本地 SQLite，不经过任何第三方。
  • 唯一的「可能后端」是凭证签发：仅当选择方案 B 时才需要一个约几十行的 Token 端点，且它不接触任何消息数据（见 2.1）。
  • 协议层与业务层隔离：所有 wire 模型（含官方命名混乱的 openid 家族）只存在于 Gateway 通道内，UI 只消费领域模型。这样官方字段一旦调整，改动被限制在一层内。

2 · 三个必须先定的决策

2.1 D1 凭证策略 —— 本项目唯一的硬约束

官方文档在鉴权章节明确写着：「为了安全考虑，请勿在应用前端使用访问凭证。请在应用服务端发起 API 访问请求。」 而本项目的需求是「APP 内置 HTTP API 调用能力发送消息」，两者天然冲突。冲突的根源在于调用链：

发送消息  →  需要 Authorization: QQBot {ACCESS_TOKEN}
ACCESS_TOKEN  →  需要用 AppID + CLIENT_SECRET 调 POST /app/getAppAccessToken 换取
              →  有效期 7200 秒，需在过期前 60 秒内换新
CLIENT_SECRET  →  只能来自开放平台管理端，没有第二种获取方式

也就是说：只要 APP 自己发消息，就必然要么持有 CLIENT_SECRET，要么在 2 小时内被用户手动重填一次 ACCESS_TOKEN。 二者必选其一，没有第三条纯本地的路。三个可选方案：

决策结果（已确认）

采用 方案 A · 纯本地：AppSecret 由用户在设置页手动输入，经 flutter_secure_storage 存入设备；APP 自行调用 POST /app/getAppAccessToken 换取 ACCESS_TOKEN，并按官方机制在过期前 60 秒窗口内静默换新。

CredentialProvider 这层抽象仍然保留：它只增加一个接口文件、不增加代理实现，收益是把「将来切换凭证来源」从一次 API 层重构降级为改 1 个文件 + 设置页多一个输入框。因此方案 C 实际落地为「方案 A + 抽象」，而不是二选一。

本决策的代价不变，需要你知悉：AppSecret 存在于设备上，在设备被 root / App 被反编译的条件下存在泄露风险，且一旦泄露等于机器人被完全接管（他人可以以你的机器人身份向所有用户发消息）。因此本形态定位为自用 / 内测，不适合作为上架发布形态。UI 上必须向用户明示这一点，防护清单见下方。

方案 A · 纯本地 已确认采用

AppSecret 存进 flutter_secure_storage，APP 自行换取与续期 ACCESS_TOKEN。

  • 零后端 完全符合「不需要额外部署公网后端服务」
  • 体验最好 配置一次永久可用
  • 违反官方安全要求
  • AppSecret 泄露 = 机器人被完全接管 可被他人以你的机器人身份对所有用户发消息
  • 仅适合自用 / 内测，不适合上架发布

方案 B · 极薄 Token 代理

一个只有 POST /token 的服务（约 30 行；可用 Cloudflare Worker / 云函数），AppSecret 只存在于该服务上。

  • 符合官方安全要求 设备上无长期密钥
  • 事件链路仍是零后端 代理只发 token，不碰消息
  • 可随时收回权限 按设备签发 access key
  • 需要一个可访问端点 与「不部署后端」有出入（但几乎零运维）

方案 C · 接口隔离，先 A 后 B 抽象保留

把凭证来源抽象成 CredentialProvider，先落地方案 A 的实现，方案 B 的实现留空位。

  • 不阻塞开工 架构上不为将来改方案返工
  • 风险可控 首期在 UI 上明确标注风险等级与适用场景
  • 已预留 设置页预留「Token 代理地址」输入项，接上即用
  • 推荐理由：这是唯一不浪费工作量的解法，切换成本约等于改 1 个文件
抽象边界怎么画（无论选 A 还是 B 都不变） 
abstract class CredentialProvider {

  void invalidate(String botId);
}

采用方案 A 时必须做的最小防护（不能省）
  • flutter_secure_storage 11.0.0，并在 Android 端设置 android:allowBackup="false"，否则系统备份还原后会抛 InvalidKeyException: Failed to unwrap key（官方插件文档明确列出的坑）。
  • 禁止把 AppSecret 写入任何日志、崩溃上报、剪贴板与截图（Android 侧对输入页设 FLAG_SECURE）。
  • 设置页对 AppSecret 字段默认掩码显示，且不做本地导出功能。
  • 发布版本关闭调试日志输出（kReleaseMode 时禁用网络日志）。
  • 凭证输入页设置 FLAG_SECURE（Android）以防截屏 / 录屏，并对 AppSecret 字段默认掩码显示、提供「显示」开关。
  • 不提供 AppSecret 的一键复制到剪贴板与本地导出功能；输入框关闭自动纠错与联想。
  • 凭证输入页常驻一行风险提示（「凭证保存在本机，仅建议自用」），并在保存时二次确认。
  • access_token 与 AppSecret 的读取统一走 CredentialProvider，业务代码不得直接持有 AppSecret 字符串。

2.2 D2 后台保活策略

这不是优化项，而是功能前提。官方对文字子频道写明「发送消息接口要求机器人接口需要连接到 WebSocket 上保持在线状态」，因此连接在线与否直接决定能力是否可用。

平台现实情况本方案策略
Android Doze / 应用待机 / 厂商省电策略会掐断长连接；Android 8.0 起后台不再收到网络变化广播 前台服务（FOREGROUND_SERVICE + FOREGROUND_SERVICE_DATA_SYNC）+ 常驻通知显示连接状态；引导用户关闭电池优化；监听 onConnectivityChanged 仅在前台可靠，回前台时主动做一次连通性检查
iOS 后台无法可靠维持 WSS；只有 audio / voip / location 等特定 UIBackgroundModes 才能长时间后台运行，滥用会被审核拒 已确认 挂起为主 + BGTaskScheduler 额外尝试唤醒：使用 Apple 正式提供的 BGAppRefreshTask / BGProcessingTask，注册标识符并在 Info.plist 声明 BGTaskSchedulerPermittedIdentifiers 与 UIBackgroundModes = fetch / processing。进入后台不假装保活；每次被唤醒或回到前台时，先把已断的 socket 重建并走 Resume，再用补齐的事件按规则补回复
BGTaskScheduler 的真实能力边界（采用后仍需接受的事实）

BGTaskScheduler 是 Apple 正式提供的后台机制，审核安全，但它不是「定时器」：何时执行、是否执行、执行多久，全部由系统决定，官方不提供任何时间保证。实际表现通常是唤醒稀疏（间隔常达十几分钟到数小时）、后台窗口只有几十秒，且 BGProcessingTask 还要求设备充电 / 空闲等条件。

因此在本方案里它的定位是尽力而为的补充：每次被唤醒时，WSS 连接早已断开，必须在窗口内完成「重建 socket → 走 Resume → 补齐事件」这条最短路径；如果窗口不够，就把进度留到下次唤醒或回前台继续。结论仍然成立——iOS 上不能把「后台实时收到并自动回复」当作可靠承诺，产品文案不要这样写。若业务上必须保证后台实时，只能改用 Webhook 公网回调，那与本项目「手机直连、不部署后端」的定位冲突。

实现上需要注意：task 标识符必须在 App 启动完成前通过 BGTaskScheduler.register 注册（且注册先于 didFinishLaunching 返回），并在每次任务结束时重新提交下一次请求；漏掉这两点会导致后台唤醒静默失效。

2.3 D3 并发连接策略

策略说明建议
单连接（同一时刻仅 1 个 Bot 在线） 切换 Bot 时先断旧连接再建新连接。省电、省流量、UI 与状态简单 未选 实现简单，但无法满足多 Bot 同时收事件的需求
多连接（多个 Bot 同时在线） 每个 Bot 一条 WSS + 独立 session/seq + 独立 access_token 缓存。官方 Session 限额是按 Bot 维度计算的，所以多个 Bot 不会互相挤占配额；但移动端耗电与内存随连接数线性上升，且 iOS 后台必然全部断开 已确认采用 连接管理器按 Map<botId, Connection> 组织，每个 Bot 独立状态机
多连接带来的三项必须落实的工程约束
  • 并发上限要可配、要有默认值。 每条连接都要独立跑心跳、独立保存 session/seq、独立重建，数量上去后耗电与内存是主要成本。建议默认上限 3，超过后按「最近使用」权重让空闲连接转入惰性（不建连，切到时再建），并在设置页显示每条连接的实时状态与流量估算。
  • 前台服务要承载 N 条连接。 Android 前台服务的常驻通知需要汇总展示「在线 N / 总数 M」并可一键全部断开，不能每个 Bot 弹一条通知。
  • 凭证与限额都要按 Bot 隔离。 access_token 缓存、session_start_limit 剩余额度、DedupGuard 去重表、消息与事件表都必须带 botId 维度，否则会出现 A 机器人的 token 被 B 机器人使用、或跨 Bot 误判重复消息这类难查的问题。

无论几条连接，shard 一律使用官方明确允许的无分片写法 [0, 1]。分片是给单 Bot 在多服务器间水平扩展用的，移动端引入分片只增加复杂度且不带来收益。

为什么「落库成功后才推进 seq」是这个设计里最要紧的一条

官方推荐「处理过事件之后记录下 s」，并说明 Resume 会自动补发这个 seq 之后的事件。如果我们在「收到」就推进 seq，一旦 App 在处理或写库过程中被杀，这段事件既没落库也不会被补发——静默丢消息，且不可恢复。反过来，如果我们推进得保守（落库后才推进），最坏情况只是 Resume 后重复补发几条，而重复推送官方本来就会发生，去重层已经覆盖。所以：宁可重复，不可丢失。

/// 事件基类：用 sealed 保证 switch 穷尽性，编译器帮我们兜住遗漏。
sealed class QqEvent {
  const QqEvent({required this.eventId, required this.seq});
  final String? eventId;
  final int? seq;

  /// 官方未提供的事件一律落到 UnknownEvent，绝不因未知 t 而中断事件流。
  static QqEvent decode(String? t, Object? d, {String? id, int? seq}) {
    final map = (d is Map) ? d.cast<String, dynamic>() : <String, dynamic>{};
    return switch (t) {
      'C2C_MESSAGE_CREATE'       => C2cMessageCreate.fromJson(map, id, seq),
      'GROUP_AT_MESSAGE_CREATE'  => GroupAtMessageCreate.fromJson(map, id, seq),
      'GROUP_MESSAGE_CREATE'     => GroupMessageCreate.fromJson(map, id, seq),
      'C2C_MSG_RECEIVE'          => C2cMsgReceive.fromJson(map, id, seq),
      'C2C_MSG_REJECT'           => C2cMsgReject.fromJson(map, id, seq),
      'GROUP_MSG_RECEIVE'        => GroupMsgReceive.fromJson(map, id, seq),
      'GROUP_MSG_REJECT'         => GroupMsgReject.fromJson(map, id, seq),
      'GROUP_ADD_ROBOT'          => GroupAddRobot.fromJson(map, id, seq),
      'GROUP_DEL_ROBOT'          => GroupDelRobot.fromJson(map, id, seq),
      'GROUP_MEMBER_ADD'         => GroupMemberAdd.fromJson(map, id, seq),
      'GROUP_MEMBER_REMOVE'      => GroupMemberRemove.fromJson(map, id, seq),
      'GROUP_JOIN_REQUEST'       => GroupJoinRequest.fromJson(map, id, seq),
      'FRIEND_ADD'               => FriendAdd.fromJson(map, id, seq),

      _                          => UnknownEvent(t: t, raw: map, eventId: id, seq: seq),

  }

时间字段必须容错解析

官方时间格式不统一：消息类事件是 RFC3339 字符串（带东八区偏移），而 FRIEND_ADD、GROUP_ADD_ROBOT、GROUP_MEMBER_ADD 等用的是 integer Unix 秒。因此统一走一个容错入口，不要在各事件里各写一套：

abstract final class QqTime {
  /// 同时接受 RFC3339 字符串与 Unix 秒整数；失败返回 null 而不是抛异常。
  static DateTime? tryParse(Object? raw) {
    if (raw is num) {
      return DateTime.fromMillisecondsSinceEpoch(raw.toInt() * 1000);
    }
    if (raw is String) {
      return DateTime.tryParse(raw);
    }
    return null;
  }
}

5 · 状态管理选型

建议：Riverpod（flutter_riverpod 3.3.1），不叠加 Bloc，不额外引入 get_it。

方案对本项目的匹配度结论
Riverpod 3.3.1 同时解决三件事：依赖注入（WSS 连接、HTTP 客户端、数据库都是长生命周期单例，需要跨页面共享且可被测试替换）、异步状态（AsyncValue 原生表达 loading / error / data，正好对应「连接中 / 连接失败 / 已连接」）、流式数据（drift 的查询本身就是 Stream，与 StreamProvider 天然契合）。编译期安全，无 BuildContext 依赖，可在纯 Dart 测试中用 ProviderContainer 覆盖依赖 采用
Bloc 事件驱动语义与本项目契合，但连接层与数据库不需要 event→state 的显式映射，会带来大量样板；且 Bloc 不含 DI，仍需再引一个容器 不采用
Provider + ChangeNotifier 足够简单，但缺少编译期安全与 AsyncValue，错误与加载态要手写；连接状态机分支多时容易漏状态 不采用
纯 StreamBuilder + 手动单例 原型阶段可行，但多 Bot 切换、依赖替换、测试注入会迅速失控 不采用
