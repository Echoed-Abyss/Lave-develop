1 · 整体架构

官方对「事件」的定义是：当用户在 QQ 平台内产生行为操作，或某些接口存在异步返回通知确认机制时，QQ 会通过事件的方式通知开发者，开发者据此进行下一步响应。典型场景包括用户给机器人发消息、用户添加机器人为好友、机器人被拉入群聊等。

来源：事件订阅与通知

事件接收有两条完全不同的通道，官方在管理端「事件订阅与回调地址」中提供切换，且切换后立刻生效。本项目选定 Gateway WSS。

1.1 双通道对比

Gateway WSS 本项目选用

官方原文定位：不依赖公网服务器部署，适合个人单机使用，需维护长连接。如果你是想用于连接 OpenClaw 等类似 AI Agent 服务，在 AI 服务提供方没有明确说明和指引的前提下，选用 WebSocket 即可。

  • 客户端主动连接腾讯网关 wss://api.bot.qq.com/websocket/
  • 专有 OpCode：1 / 2 / 6 / 7 / 9 / 10 / 11
  • 有心跳、有分片、有断线补发（Resume）

Webhook 回调

官方原文定位：事件推送至你配置的 HTTPS 服务上，适合提供公开服务的机器人使用，运维更可靠。

  • 腾讯主动推送到开发者公网后端
  • 专有 OpCode：12（HTTP Callback ACK）、13（回调地址验证）
  • 回调地址允许端口：80、443、8080、8443
  • 鉴权靠 Ed25519 签名（X-Signature-Ed25519 + X-Signature-Timestamp + Body）

1.2 移动端可行性结论

结论：Flutter / Android / iOS 客户端可以直接建立 WSS 长连接并监听事件

官方对 WebSocket 的原文定位即为「不依赖公网服务器部署，适合个人单机使用」，因此「获取接入点 → 建连 → Identify → 持续接收 Dispatch 事件」这一整条链路在移动端本地即可完成，事件监听能力无需公网后端中转。

但必须正视一处官方硬性要求（移动端最大风险点）

官方在鉴权章节明确写着：「为了安全考虑，请勿在应用前端使用访问凭证。请在应用服务端发起 API 访问请求。」 这意味着把 AppSecret 打进 App 包内去换取 access_token，与官方安全要求直接冲突，且 AppSecret 一经反编译即泄露，可被他人完全接管机器人。

正确解法（在进入架构设计时需专门讨论）：事件接收走移动端本地 WSS，而 access_token 的获取与刷新交由一个极薄的代理服务完成，App 只持有短期 token；或使用官方推荐的云函数/服务器中转。这一点不能靠「把 secret 混淆进代码」蒙过去。

另一处需要提前知晓的限制

官方在消息发送章节写明：「发送消息接口要求机器人接口需要连接到 WebSocket 上保持在线状态」（文字子频道章节原文）。即 WSS 连接是否在线，会影响部分发送能力，这决定了移动端 App 的「保活」不是可选优化，而是功能前提。

2.3 有效期与刷新策略

  • 生命周期默认 7200 秒（2 小时），过期后需自行刷新。
  • 有效期内重复获取会返回相同的值，不会刷新出新 token。
  • 在上一个 token 接近过期 60 秒内获取时，会得到一个新的 token；老 token 在这 60 秒内仍然有效。
  • 官方建议：在服务端设置定时刷新凭证的业务逻辑，以防过期。

3.3 通用 Payload 结构

官方原文：payload 指的是在 webhook 或 websocket 连接上传输的数据，网关的上下行消息采用的都是同一个结构。

{
  "id": "event_id",
  "op": 0,
  "d": {},
  "s": 42,
  "t": "GATEWAY_EVENT_NAME"
}
字段描述（官方原文）
id事件 id
op指的是 opcode，参考连接维护
s下行消息都会有一个序列号，标识消息的唯一性，客户端需要在发送心跳的时候，携带客户端收到的最新的 s
t代表事件类型。主要用在 op 为 0 Dispatch 的时候
d代表事件内容，不同事件类型的事件内容格式都不同，请注意识别。主要用在 op 为 0 Dispatch 的时候
压缩传输：官方文档未提供

官方全部相关页面中未出现 zlib、deflate、compress、inflate 等任何压缩相关表述，payload 示例中也没有 compress 字段。不要按其他平台的经验假设存在压缩协商，实现时按「纯 JSON 文本帧」处理，并在真机验证中确认。

3.7 Session、seq 与分片

Session 与 seq

  • session_id 通过 Op2 Identify 登录鉴权成功后获得，出现在 READY 事件的 d.session_id。
  • 只有登录成功后，QQ 后台才会下发事件通知。
  • seq 即事件流中的 s；Resume 时把最后处理过的 s 传回，网关自动补发其后的所有事件。
  • 官方示例中 READY 的 s = 1、RESUMED 的 s = 2002。
官方文档未提供

s 是否严格从 1 开始并严格 +1 递增、是否与 shard 相关、断线期间是否连续；session_id 的有效期；「短时间内重连」的具体时限；同一 session_id 可 Resume 的次数上限。实现上不得依赖 s 连续递增这一假设，只能把它当作「最后已处理位置的水位标记」。

Session 创建限额

官方原文：每个机器人创建的连接数不能超过 remaining 剩余连接数。 限额信息来自 /gateway/bot 的 session_start_limit（total / remaining / reset_after / max_concurrency）。

分片机制

官方原文：随着 bot 的增长并被添加到越来越多的频道中，事件越来越多，业务有必要对事件进行水平分割，实现负载均衡。机器人网关实现了一种用户可控制的分片方法，该方法允许跨多个网关连接拆分事件。分片完全由用户控制，并且不需要在单独的连接之间进行状态共享。

分片哈希规则（官方原文）：

shard_id = (guild_id >> 22) % num_shards

即：分片按频道 id 哈希，同一个频道的信息会固定从同一个连接推送。

移动端实操建议

官方明确「若无需分片，使用 [0, 1] 即可」。以单机 App 运行机器人时，shard 传 [0, 1] 即可完整接收事件；分片是给多连接水平扩展用的，移动端场景通常不需要。

官方文档未提供

max_concurrency（每 5s 可创建的 Session 数）的具体节流实现方式；shard 第二个元素是否必须等于 /gateway/bot 返回的建议 shards；分片与 intents 的关系、每个分片是否独立 session_id。

官方原文：如开发者需要接收用户 at 机器人的消息，那么就需要在 intents 中设置接收 PUBLIC_GUILD_MESSAGES。则需要先计算 1 << 30 的值。然后与 0 做位或操作，得到最终需要传递的 intents。如果涉及到多个事件类型的接收，则需要将多个结果做位或操作，如：0|1<<30|1<<1 代表订阅 PUBLIC_GUILD_MESSAGES 和 GUILD_MEMBERS 这两类事件。

「群聊 + 单聊 + 频道」的推荐 intents 组合值；1 << 2 ～ 1 << 8、1 << 11、1 << 13 ～ 1 << 23、1 << 31 及以上各位的含义；Identify 示例中 "intents": 513 具体对应哪些 intent（按表达式可换算为 1<<9 | 1<<0，但这属于换算推断，非官方原文）。

4.2 intents 权限规则

默认有权限（基础事件）GUILDS、PUBLIC_GUILD_MESSAGES、GUILD_MEMBERS
其他特殊事件都需要经过申请才能够使用
传了无权限 intentswebsocket 会报错，并直接关闭连接（相关错误码 4013 无效的 intent、4014 intent 无权限）
权限被取消后的行为当前连接上不会报错，但收不到对应事件类型；重新连接则报错，所以权限被取消后需及时调整监听代码，避免无法连接

官方提醒原文：请开发者注意订阅事件的范围需要控制在自己所需要的范围之内。

本项目的最小 intents 建议

移动端只做单聊与群聊时，最小必需位为 GROUP_AND_C2C_EVENT (1 << 25)；若还要处理按钮点击回调，需叠加 INTERACTION (1 << 26)；若还要处理群成员进出与加群申请，需叠加 GROUP_MEMBER_EVENT (1 << 24)（该位未被官方列入 intents 清单，属于需实测确认项）。切勿为了省事而订阅全量 intents，无权限位会直接导致连接被关闭。

去重机制（官方原文）

为了确保消息可到达，极端情况下，相同的 msg_id 的消息会有概率重复推送。如果开发者不对 msg_id 的回复做存储排重，很可能会回复两条相同的消息给用户。官方因此引入 msg_seq 字段，便于过滤重复消息响应。移动端实现必须落地 msg_id 级别的去重表（本地 SQLite / 内存 LRU 均可，注意 App 重启后的持久化）。

另有官方表述（send-receive/event.html）：当群主设定允许该机器人接收群内全部消息时，机器人可接收到群内所有成员在群内的发言消息。

该事件不在 GROUP_AND_C2C_EVENT 的官方 intents 清单中

官方 intents 清单里 GROUP_AND_C2C_EVENT (1<<25) 只列出了 GROUP_AT_MESSAGE_CREATE，未列 GROUP_MESSAGE_CREATE。该事件的 intent 归属需要以真机实测确认（属于「官方文档未提供明确归属」项）。

频道（QQ频道）事件与单聊/群聊事件是两套独立的数据模型：MessageAttachment 在频道体系只有 url 一个字段，而 C2C/群聊体系有 8 个字段；频道的 id 是数字型 guild_id/channel_id，单聊/群聊是 openid 字符串。实现时必须按 t 分派到不同的解析器，不能共用模型。

8.2 心跳与 seq 的落地要点

  • 心跳周期必须用 Hello 返回的 heartbeat_interval（毫秒，官方示例 45000），不要硬编码。
  • 心跳包 d 传「客户端收到的最新的 s」；首次连接传 null。
  • 收到 Op11 才认为本轮心跳成功；官方未给出失败阈值，需自行取 heartbeat_interval 的 1～2 倍作为判据并主动断连重连。
  • seq 的持久化：官方推荐「处理过事件之后记录下 s」，注意是「处理完成后」而非「收到时」。移动端必须把 session_id 与 seq 落盘，否则 App 进程被杀后无法 Resume。
  • 按官方规则，s 不能假设严格 +1 递增，只能作为水位标记。

12 · 开发红线

禁止引入任何非官方协议实现

后续所有开发严格以 QQ 机器人开放平台官方文档（api-v2）为唯一实现依据。明令禁止以下方案，且不接受任何形式的绕过：

  • 逆向 QQ 客户端协议：自行实现 QQ 私有登录 / 收发消息协议，或使用他人已逆向的协议库。
  • 抓包与协议复用：通过抓取 QQ 客户端或第三方客户端的通信流量，提取内部接口、密钥与签名算法并用于自建服务。
  • Hook / 注入 / 改包：对 QQ 客户端做 Xposed、Frida、LSPosed、动态库注入、重打包等改造，或使用「协议机」「协议号」「PC 协议端」类方案。
  • 模拟 QQ 客户端登录：以单个 QQ 账号身份登录并伪装为用户或机器人，包括但不限于「个人 QQ 号挂机器人」「协议框架搭建的机器人」。
  • 使用非官方 SDK / 私有接口：任何未在官方文档中列出的接口、域名、字段与枚举。

这类做法违反 QQ 开放平台运营规范与用户协议，会导致账号与机器人被封禁（对应错误码 4915、11265），并存在账号被盗、隐私泄露与法律风险。若后续提出此类需求，将直接拒绝并说明风险。

合规实现边界（本项目允许并鼓励的范围）
  • 使用官方 Gateway WSS（wss://api.bot.qq.com/websocket/）接收事件，移动端本地直连，不依赖公网后端。
  • 使用官方 OpenAPI（https://api.bot.qq.com）发送与撤回消息、上传富媒体。
  • 使用 AppID + AppSecret 换取 access_token（换取环节需放在服务端/代理，避免在客户端存放 AppSecret）。
